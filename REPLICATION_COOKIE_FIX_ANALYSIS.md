# Replication Cookie Persistence Issue - Analysis and Fix Plan

## Date
October 7, 2025

## Problem Summary
The replication consumer repeatedly receives all data from the provider instead of performing incremental synchronization. The consumer does not persist or load the replication cookie between sync cycles, causing it to request a full sync every time.

## Root Cause Analysis

### Issue 1: StateManagerImpl Never Persists to Disk
**Location**: `src/replication.rs`, lines 822-849

**Current Implementation**:
```rust
#[async_trait]
impl StateManager for StateManagerImpl {
    async fn save_cookie(&self, cookie: &str) -> Result<(), ConsumerError> {
        *self.cookie.lock().unwrap() = Some(cookie.to_string());

        // In production, persist to file/database
        // For now, just keep in memory

        Ok(())
    }

    async fn load_cookie(&self) -> Result<Option<String>, ConsumerError> {
        Ok(self.cookie.lock().unwrap().clone())
    }
    // ... other methods
}
```

**Problem**: The `save_cookie` method only stores the cookie in memory (Arc<Mutex<Option<String>>>). It never writes to the file system at `storage_path`. When the server restarts or the consumer FSM resets, the cookie is lost.

**Evidence**: The configuration specifies `state_storage_path = "./data/replication_state"`, but the directory remains empty:
```
$ ls -la ./data/replication_state
total 0
drwxr-xr-x@ 2 kasunranasinghe  staff   64 Oct  7 21:45 .
drwxr-xr-x@ 5 kasunranasinghe  staff  160 Oct  7 21:45 ..
```

### Issue 2: Consumer FSM Never Loads Cookie Before Sync
**Location**: `src/replication_consumer_fsm.rs`, line 825-885

**Current Implementation**:
```rust
async fn handle_start_consumption(
    &mut self,
    provider_url: String,
    cookie: Option<String>
) -> Result<Option<usize>, ConsumerError> {
    // ... validation ...
    
    // Store provider URL and cookie
    self.provider_url = Some(provider_url.clone());
    self.current_cookie = cookie.clone();  // <-- Uses passed-in cookie (always None)
    self.session_start = Some(Instant::now());
    
    // ... connects to provider ...
    
    // Request entries from cookie
    let entries = self.provider_connection.request_from_cookie(cookie.as_deref()).await
        .map_err(|e| ConsumerError::ConnectionError { 
            message: format!("Failed to request entries from cookie: {}", e) 
        })?;
```

**Problem**: The FSM accepts a `cookie` parameter but never loads the persisted cookie from `state_manager.load_cookie()`. The consumer service passes `None` for the cookie:

**Location**: `src/replication_service.rs`, line 430-436
```rust
// Start sync by sending StartConsumption event
let event = ReplicationConsumerEvent::StartConsumption {
    provider_url: provider_url.clone(),
    cookie: None, // Will be loaded from state by FSM  <-- NEVER HAPPENS!
};
```

### Issue 3: Consumer FSM Never Persists Cookie After Sync
**Location**: `src/replication_consumer_fsm.rs`, line 870-880

**Current Implementation**:
```rust
// Process the batch
self.batch_processor.process_batch(entries).await
    .map_err(|e| ConsumerError::ProcessingError { 
        message: format!("Failed to process batch: {}", e) 
    })?;

// After processing, go to listening state (skip cookie persistence for now)
self.state = ReplicationConsumerState::Listening;  // <-- COMMENT SAYS "skip cookie persistence"
```

**Problem**: After processing entries, the FSM transitions directly to `Listening` state without persisting the new cookie. The comment explicitly states "skip cookie persistence for now", meaning this was left as a TODO.

### Issue 4: No CSN-Based Cookie from Provider
**Location**: Multiple files in replication chain

The provider needs to return a cookie representing the highest CSN (Change Sequence Number) processed. This cookie should be:
1. Generated by the provider after sending entries
2. Returned to the consumer
3. Extracted and persisted by the consumer
4. Used in the next sync request

Currently, there's no clear flow for the provider to communicate "here's the cookie representing what I just sent you".

## Impact

1. **Network Overhead**: Every sync cycle transfers all entries, not just changes
2. **Processing Overhead**: Consumer reprocesses all entries every sync
3. **No Incremental Sync**: Defeats the purpose of CSN-based replication
4. **Memory Waste**: Full dataset transferred repeatedly
5. **Database Churn**: Unnecessary updates to existing entries

## Required Fixes

### Fix 1: Implement Persistent Cookie Storage
**File**: `src/replication.rs`
**Changes**: 
- Implement file-based persistence in `StateManagerImpl::save_cookie()`
- Implement file-based loading in `StateManagerImpl::load_cookie()`
- Add proper error handling for I/O operations
- Create state storage directory if it doesn't exist
- Use atomic file writes to prevent corruption

**Implementation Details**:
- Cookie file format: Simple text file containing the CSN cookie string
- File path: `{storage_path}/replication_cookie.txt`
- Atomic write: Write to temporary file, then rename
- File locking: Not needed (single consumer process)

### Fix 2: Load Cookie Before Each Sync
**File**: `src/replication_consumer_fsm.rs`
**Changes**:
- In `handle_start_consumption()`, load cookie from state_manager if not provided
- Use loaded cookie as fallback when `cookie` parameter is None
- Log whether using new cookie or loaded cookie

**Implementation Details**:
```rust
async fn handle_start_consumption(
    &mut self,
    provider_url: String,
    cookie: Option<String>
) -> Result<Option<usize>, ConsumerError> {
    // Load cookie from state if not provided
    let cookie = match cookie {
        Some(c) => {
            log::info!("Using provided cookie: {}", c);
            Some(c)
        }
        None => {
            log::info!("Loading cookie from state manager");
            self.state_manager.load_cookie().await
                .map_err(|e| ConsumerError::StateError { 
                    message: format!("Failed to load cookie: {}", e) 
                })?
        }
    };
    
    if let Some(ref c) = cookie {
        log::info!("Starting sync from cookie: {}", c);
    } else {
        log::info!("Starting full sync (no cookie)");
    }
    
    // ... rest of implementation
}
```

### Fix 3: Persist Cookie After Successful Sync
**File**: `src/replication_consumer_fsm.rs`
**Changes**:
- After processing batch, extract new cookie from response
- Transition to `PersistingState` state (not directly to `Listening`)
- Call `state_manager.save_cookie()` with new cookie
- Only transition to `Listening` after successful persistence

**Implementation Details**:
- Provider must return cookie in response (see Fix 4)
- Consumer must extract cookie from provider's response
- Handle persistence errors appropriately
- Log cookie persistence for debugging

### Fix 4: Provider Returns Cookie in Response
**File**: `src/replication.rs` (ChangelogProviderImpl)
**Changes**:
- Modify `ProviderConnection::request_from_cookie()` to return both entries and new cookie
- Provider generates cookie from highest CSN in returned batch
- If returning all entries, cookie represents the latest CSN in changelog

**Implementation Details**:
```rust
pub struct SyncResponse {
    pub entries: Vec<Vec<u8>>,
    pub cookie: Option<String>,  // CSN-based cookie for next sync
    pub complete: bool,           // Whether sync is complete
}
```

### Fix 5: Consumer Extracts and Uses Cookie
**File**: `src/replication_consumer_fsm.rs`, `src/replication.rs`
**Changes**:
- Update trait definitions to support cookie in response
- Consumer extracts cookie from SyncResponse
- Consumer persists cookie after processing
- Consumer uses cookie in next request
